1Fundamentos e princípiosDefinição IEEE, camadas, essência da prática, 7 princípios de Hooker, processo e o caso Winburg
Ideia centralEngenharia de software é tratar software como engenharia: com processo, disciplina e medição, sempre com o foco na qualidade como base.

Definição (IEEE)

“A aplicação de uma abordagem sistemática, disciplinada e quantificável no desenvolvimento, na operação e na manutenção de software; isto é, a aplicação de engenharia ao software.”

Visão em camadas

Foco na qualidade→Processo→Métodos→Ferramentas

A qualidade é a pedra fundamental. O processo é a “liga” que mantém as camadas coesas e permite desenvolver de forma racional e no prazo.

Essência da prática

PassoCorresponde a
1. Compreender o problemaComunicação e análise
2. Planejar uma soluçãoModelagem e projeto de software
3. Executar o planoGeração de código
4. Examinar o resultadoTestes e garantia da qualidade

Os 7 princípios de Hooker

PrincípioEm uma frase
1. A razão de existirO software existe para agregar valor ao usuário. “Isso agrega valor real?” Se não, não faça. Base de todos.
2. KISSKeep It Simple, Stupid: o mais simples possível, mas não simplista.
3. Mantenha a visãoIntegridade conceitual; sem “colcha de retalhos”.
4. O que um produz, outros consomemAlguém vai ler, manter e depurar o que você fez.
5. Esteja aberto para o futuroTudo muda em meses; pergunte sempre “e se…?”.
6. Planeje a reutilizaçãoReduz custo e aumenta valor; é a meta mais difícil.
7. Pense!Pensar antes de agir; reconhecer quando não se sabe algo.

Processo de software

Conjunto estruturado de atividades e práticas para desenvolver, manter e entregar software. Define como o trabalho será feito, quem fará, quando e com quais recursos. Dá estabilidade, controle e organização. O processo certo depende do produto: um software de avião não segue o mesmo processo de um app ou de um videogame.

Todo projeto nasce de uma necessidade de negócio: corrigir um defeito, adaptar um sistema legado, ampliar funções ou criar um novo produto.

Miniestudo de caso: Winburg

Ônibus com máquina que aceita só cédulas de $1, validadas por reconhecimento de imagem. Requisitos: precisão ≥ 98% e resposta < 1 s.

  • Falso positivo (aceitar papel falso) → perda de receita.
  • Falso negativo (recusar cédula válida) → afasta usuários.
  • Fracasso: precisão abaixo de 98%, validação lenta (filas), RNF críticos ignorados, falta de testes rigorosos e desprezo pela experiência do usuário.
PegadinhaO sistema de Winburg “funcionava” (o RF de aceitar cédulas existia). Quem derrubou o projeto foram os requisitos não funcionais: precisão e tempo de resposta.
2Modelos de ciclo de vidaPrescritivos × ágeis, cascata, V, incremental, espiral, prototipagem, RAD, software aberto e sincronizar-e-estabilizar
Ideia centralModelos de processo existem para organizar, orientar e sistematizar o desenvolvimento: estruturam o trabalho, facilitam planejamento e controle, reduzem riscos, melhoram a comunicação e se adaptam a contextos diferentes.

Prescritivos × ágeis

  • Prescritivos (tradicionais ou clássicos): ordenados e sequenciais; prescrevem atividades, artefatos e controles. Ex.: cascata, incremental, evolucionários (espiral, prototipação), Modelo V, RAD.
  • Ágeis: alternativa baseada no Manifesto Ágil; adaptabilidade, colaboração com o cliente e entrega contínua. Ex.: Scrum, Kanban, XP.

Cascata (sequencial linear)

Requisitos→Projeto→Implementação→Teste→Implantação

Cada fase depende da conclusão da anterior. Usar quando os requisitos são bem compreendidos e estáveis, com pouca mudança e muita necessidade de documentação.

Pontos fortes
  • Rigor e disciplina (documentação e verificação por fase)
  • Facilidade de gestão
  • Controle de qualidade por fase (SQA)
  • Previsibilidade (ambientes regulados)
Pontos fracos
  • Pouca flexibilidade a mudanças
  • Dependência de documentação que o cliente não entende
  • Validação tardia: o cliente só vê o produto no fim
  • Risco de não atender às expectativas reais

Outros modelos prescritivos

Prototipagem rápida

Protótipo rápido = modelo operacional funcionalmente equivalente a um subconjunto do produto. Ex.: para contas a pagar/receber e estoque, ele captura dados na tela e imprime relatórios, mas não atualiza arquivos nem trata erros. O cliente experimenta; quando estiver satisfeito, a equipe escreve a especificação. Resultado: menos “voltas” de realimentação que no cascata.

Espiral

É como um cascata em que cada fase é precedida por análise de riscos (às vezes com protótipo). Se um risco significativo não puder ser minimizado, o projeto é encerrado ou segue em escala menor. Dimensão radial = custo acumulado; dimensão angular = progresso. Cada ciclo = uma fase, começando pelos objetivos, alternativas e restrições. Em 25 projetos, a produtividade subiu ≥ 50% (100% na maioria).

Software aberto (open source)

  1. Fase 1: uma pessoa tem a ideia (Linux, Firefox, Apache), constrói uma versão inicial e distribui de graça.
  2. Fase 2: com interesse, usuários viram codesenvolvedores: relatam defeitos, propõem correções, estendem e portam o programa.

Trabalho voluntário; um grupo central de mantenedores gerencia e garante as correções; o grupo periférico relata defeitos de vez em quando. Tem em comum com codificar-e-corrigir e prototipagem o fato de gerar logo uma versão operacional.

ManutençãoO que é
CorretivaRelatar e corrigir defeitos
De aperfeiçoamentoAcrescentar funcionalidade
AdaptativaPortar para um novo ambiente

Sincronizar-e-estabilizar (Microsoft)

Versão do iterativo-incremental usada pela Microsoft (Cusumano e Selby, 1997). Entrevistas com futuros clientes → lista de recursos prioritários → especificação → 3 ou 4 incorporações (a 1ª com os recursos mais fundamentais).

  • Desenvolvimento paralelo: pequenas equipes em módulos diferentes ao mesmo tempo.
  • Sincronização frequente: no fim de cada dia, juntam os componentes, testam e depuram.
  • Estabilização periódica: no fim de cada incorporação, corrigem as falhas e congelam a incorporação.
PegadinhaEspiral = riscos. Modelo V = verificação e validação. Incremental = entregas em partes. Não confunda os três.
3Requisitos, UML e especificaçãoLevantamento × análise, modelo de negócio, entrevistas, caso de uso, documento de especificação, RF × RNF
Ideia centralO objetivo real do levantamento é determinar qual software o cliente precisa. Começa pelo domínio, passa pelo modelo de negócio e é refinado por iteração.

Fluxo de levantamento

Conhecer o campo de aplicação→Modelo de negócio (UML)→Necessidades preliminares→Refinar (iterar)
  • Levantamento (ou captura) de necessidades: descobrir o conjunto preliminar.
  • Análise de necessidades/requisitos: refinar e estender esse conjunto.
  • Modelo de negócio: descrição dos processos de negócio da organização (ex.: banco: depósitos, empréstimos, investimentos). Dá a visão do negócio como um todo.

Diagramas UML

Ferramentas de modelagem visual da estrutura, do comportamento e da funcionalidade. Vantagens: simplificam a complexidade, melhoram a comunicação (inclusive com não técnicos), ajudam no design antes de implementar, documentam e apoiam análise e planejamento.

Caso de uso (exemplo bancário): atores Customer (cliente) e Teller (caixa) — bonecos de palito — e a oval Withdraw Money (saque). O ator é externo ao produto e desempenha um papel; o retângulo é o produto de software.

Documento de especificação

É um contrato entre cliente e desenvolvedor: diz precisamente o que o produto deve fazer e suas restrições. Parte vital: os critérios de aceitação, testes que provam que o produto atende à especificação e que o trabalho está feito.

4Métodos ágeisFilosofia, agilidade, processo ágil, Scrum (papéis, artefatos, eventos), XP e Kanban
Ideia centralÁgil = filosofia + princípios: satisfação do cliente, entrega incremental antecipada, equipes pequenas e motivadas, métodos informais, artefatos mínimos e simplicidade. A entrega tem prioridade sobre análise e projeto.

Perguntas-chave

PerguntaResposta
Quem realiza?Uma equipe ágil auto-organizada (engenheiros, gerentes, clientes, usuários).
Por que é importante?Ambientes mudam rápido; o ágil entrega sistemas corretos rapidamente.
Quais etapas?“Engenharia de software light”: comunicação, planejamento, modelagem, construção e entrega, como tarefas mínimas.
Qual o artefato?Um incremento de software operacional. Documentos: histórias de usuário e casos de teste.
Como saber se está certo?A equipe concorda que o processo funciona e entrega incrementos que satisfazem o cliente.

Agilidade não é só rapidez: é adaptar-se às mudanças entregando valor contínuo e mantendo a qualidade. Envolve velocidade, adaptação, qualidade e colaboração. Processo ágil: iterativo e incremental, flexível a mudanças (bem-vindas até no fim), foco no cliente, colaboração (dailies), entrega contínua de valor e melhoria contínua.

Scrum

Backlog do produto→Sprint Planning→Backlog do sprint→Sprint (2–4 sem.) + Daily→Incremento→Retrospectiva
PapelResponsabilidades
Product OwnerPrioriza o backlog do produto, define a meta do sprint, é o único que encerra ou estende o sprint.
Scrum MasterFacilitador: conduz a daily, remove obstáculos, orienta a equipe, ajuda o PO com o backlog, lidera a retrospectiva.
Equipe de desenvolvimento (3–6)Define como fazer e quando o incremento está pronto. Não adiciona tarefas sem cancelar/reiniciar o sprint.
EventoDetalhes
Sprint PlanningTodos. PO e devs organizam o backlog por importância/complexidade; PO define a meta; SM e devs escolhem os itens do backlog do sprint.
Daily Scrum15 min, início do dia. Obrigatórios: SM e devs (PO às vezes). 3 perguntas: o que fiz? que obstáculos tenho? o que farei?
RetrospectivaAté 3 h (sprint de 4 semanas), antes do próximo planning. SM e devs: o que deu certo, o que melhorar, compromisso.

Backlog do produto: lista priorizada do que agrega valor; nunca está completo. Backlog do sprint: itens escolhidos para o sprint atual. Incremento: código funcional entregue.

Kanban

Sistema visual: as tarefas são cartões que se movem pelas colunas de um quadro (A fazer → Em andamento → Em teste → Feito).

PegadinhaQuem encerra o sprint é o PO, não o Scrum Master. E as 3 perguntas “deu certo / melhorar / compromisso” são da retrospectiva, não da daily. (A apostila cita sprints de 2–4 semanas e, em outro slide, 3–4; na dúvida, 2–4.)
5Arquiteturas de softwareMVC, MVVM, Hexagonal (Ports and Adapters) e Clean Architecture
Ideia centralTodas separam responsabilidades. Quanto mais para a direita (MVC → MVVM → Hexagonal → Clean), mais desacoplamento e testabilidade — e mais custo inicial.

MVC — Model, View, Controller

  • Model: regras de negócio e acesso a dados · View: interface · Controller: recebe requisições, interpreta e coordena Model e View.
  • Resolve: mistura de lógica de negócio com interface; facilita manutenção da UI e trabalho em equipes.
  • Onde: web tradicional (páginas renderizadas no servidor), desktop simples, fluxo requisição → resposta.
  • Tecnologias: Django, Ruby on Rails, Laravel, ASP.NET MVC, Spring MVC; Java Swing/SWT, Windows Forms.
  • Separação clara, fácil de ensinar, frameworks maduros, Models reutilizados em várias Views. God Controllers, não escala para UIs muito ricas, perdeu espaço no front com as SPAs.

MVVM — Model, View, ViewModel

  • Evolução do MVC/MVP para UIs reativas. ViewModel expõe dados e eventos reativos à View via data binding.
  • Resolve: desacopla a UI do código, deixa a View declarativa, reduz código de sincronização.
  • Onde: UIs complexas e interativas, apps mobile, formulários dinâmicos.
  • Tecnologias: Angular, Vue, Knockout; Android ViewModel, SwiftUI; WPF, WinUI, Avalonia; Flutter (Provider, Riverpod, MobX).
  • View simples, alta testabilidade, menos boilerplate. Curva para iniciantes, binding dificulta a depuração, ViewModels gigantes.

Hexagonal — Ports and Adapters

Adapters (BD, API, UI)⇄Ports (interfaces)⇄Core / domínio
  • Separa o núcleo das interfaces externas. Ports = interfaces que o domínio expõe ou precisa. Adapters = implementações que ligam ao mundo externo.
  • Baseada em desacoplamento forte e inversão de dependência: trocar banco, UI ou API sem afetar o domínio; testar o domínio sem infraestrutura.
  • Onde: sistemas corporativos grandes, microsserviços, longa vida útil, regras de negócio complexas.
  • Tecnologias: Spring Boot, Quarkus, Micronaut, NestJS, Adonis, FastAPI, Django customizado, ASP.NET Core. Relacionadas: Clean, Onion, DDD.
  • Máximo desacoplamento, domínio limpo e testável. Estrutura inicial complexa, “overkill” para sistemas simples, mais camadas, exige disciplina.

Clean Architecture (Uncle Bob)

Criada por Robert C. Martin. Camadas concêntricas, de dentro para fora:

Entities←Use Cases←Interface Adapters←Frameworks & Drivers
  • Entities: regras de negócio de alto nível · Use Cases: orquestram a lógica da aplicação · Interface Adapters: DTOs, Presenters, Gateways, Controllers · Frameworks & Drivers: BD, UI, web, mensageria.
  • Dependency Rule: dependências só apontam para dentro; o núcleo nunca depende de detalhes (DB, UI, HTTP são “plugins”).
  • Testabilidade máxima, domínio protegido, trocar SQL por NoSQL sem mexer no domínio. Alto custo inicial, muitos arquivos e interfaces, demais para CRUDs simples.
Quando usar cada umaMVC: sistema simples/CRUD, framework já organizado assim, equipe iniciante. MVVM: UI complexa e reativa (mobile/SPA), alta testabilidade. Hexagonal/Clean: domínio complexo, muitas integrações, independência de infraestrutura, software que vai evoluir por anos.
6Testes e TDDObjetivos, caixa-branca/preta/cinza, unitário × integração, tipos por propósito, Red-Green-Refactor, xUnit e AAA
Ideia centralTestar é verificar e validar se o software funciona como esperado, encontrando defeitos antes da entrega e garantindo RF e RNF.

Objetivos: detectar erros cedo, evitar retrabalho, melhorar a manutenção, aumentar a confiança na entrega.

TDD — Test-Driven Development

Escrever os testes automatizados antes do código. O código nasce para passar nos testes; cada funcionalidade começa com um teste que falha.

Red: teste que falha→Green: código mínimo→Refactor: melhorar mantendo verde
Benefícios
  • Qualidade desde o início; menos bugs
  • Refatoração segura
  • Design mais modular
  • Documentação viva
  • Menos manutenção, mais confiança
Desafios
  • Exige mudança de mentalidade
  • Aumenta o tempo inicial
  • Difícil testar código mal projetado
  • Precisa de boa cobertura
  • Nem tudo é testável (ex.: interface gráfica)

xUnit: o mais usado no .NET moderno, integrado ao dotnet test. [Fact] = teste simples; [Theory] = vários casos de entrada.

Padrão AAA

[Fact]
public void Somar_RetornaSoma()
{
    // Arrange: preparar
    var calc = new Calculadora();
    // Act: executar
    var r = calc.Somar(2, 3);
    // Assert: verificar
    Assert.Equal(5, r);
}

Boas práticas: testes pequenos e independentes, nomes descritivos, automáticos e rápidos, mocks e stubs para dependências externas, TDD integrado ao CI/CD.

PegadinhaNo Green escreve-se o código mínimo; melhorar é no Refactor. E caixa-branca olha o código por dentro, caixa-preta não.
